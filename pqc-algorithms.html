01 / ALGORITHM FIELD NOTES

Six entries, several security assumptions

PQC is a set of classical cryptographic constructions intended to resist known classical and quantum attacks. It is not one algorithm, and it does not require a quantum computer. Read each family through four questions: what problem does it solve, what makes forgery or key recovery hard, how does the legitimate computation work, and what must an implementation preserve?

02 / ALGORITHM FIELD NOTES

ML-KEM: cancel a structured mask, then validate the ciphertext

ML-KEM uses arithmetic in Rq = Zq[X]/(X²⁵⁶+1), with q=3329. Vectors of ring elements form a module. A public matrix A is expanded from a seed; small secret and error vectors produce t=As+e. Recovering s from these noisy public relations is related to Module-LWE. The module rank and noise/compression parameters vary with the parameter set. NTT accelerates polynomial multiplication; it is an implementation tool, not the security assumption.

Teaching view of the internal PKE: t = As + e u = Aᵀr + e₁ v = tᵀr + e₂ + Encode(m) v − sᵀu = Encode(m) + eᵀr + e₂ − sᵀe₁ (mod q)

The large shared term cancels, leaving the encoded message plus bounded noise. Rounding recovers m when the specified error bounds hold. The equation omits the exact NTT representation, compression and serialization; it is not a replacement implementation. The internal K-PKE is not exposed as an approved standalone encryption service.

Encapsulation samples a fresh 32-byte internal message m, derives a candidate shared secret and encryption coins from m and the encapsulation-key hash, then encrypts m. Decapsulation decrypts m′, derives the same quantities, re-encrypts and compares c′ with c. A correctly encoded ciphertext that fails this comparison selects the specified secret-derived fallback key by implicit rejection. Key/ciphertext length and format checks still apply; rejection behavior must not leak secret-dependent information.

ML-KEM-512/768/1024 all output a 32-byte shared secret. The suffix is not its length. Authentication and transcript-bound key derivation belong to the protocol: an unauthenticated public-key substitution is not solved by the KEM alone.

03 / ALGORITHM FIELD NOTES

ML-DSA: a challenge, a masked response and carefully chosen aborts

ML-DSA works over degree-256 polynomial rings with q=8380417. It combines Module-LWE-related hiding with short-relation hardness in a Fiat–Shamir signature construction. The secret contains small vectors s₁,s₂; the public relation is t=As₁+s₂. A signing mask y creates a commitment w=Ay. The message representative μ includes the appropriate public-key/message context.

Unrounded teaching relation: c ← challenge(μ, HighBits(Ay)) z = y + c·s₁ Az − c·t = Ay − c·s₂ Actual public key: t₁ = rounded high bits of t; signature includes hints.

Hashing μ and HighBits(w), then applying SampleInBall, produces a sparse polynomial challenge c that binds the commitment to the message. The response z allows a verifier to reconstruct the required high bits without knowing y or the secret. The actual scheme transmits rounded t₁, so bounded hints repair the high-bit information lost through rounding. Verification checks challenge consistency, response norms, hint weight and valid encodings; checking just one algebraic equation is insufficient.

Signing rejects attempts with unsuitable bounds and samples another mask. This protects the output distribution from revealing the secret and keeps verification correct. Removing the rejection conditions to improve speed changes the scheme. FIPS 204 supports hedged and deterministic signing variants; both still require correct mask derivation and domain separation.

Parameter sets are ML-DSA-44, -65 and -87, named after matrix dimensions, not signature bit lengths. Pure ML-DSA and HashML-DSA are distinct standardized interfaces; an application cannot substitute an arbitrary prehash. Audit arithmetic, rejection loops, randomness, faults and side-channel behavior separately.

04 / ALGORITHM FIELD NOTES

SLH-DSA: hash chains, a forest and an authenticated hypertree

SLH-DSA relies on hash-based constructions rather than lattice equations. Its public key contains a public seed and a top-level Merkle root; secret seeds derive the many underlying signing secrets. Each signature starts with a message-dependent randomization value R and a digest that selects FORS leaves and a position in a large hypertree.

FORS signs digest bits using a forest of small trees: selected secret values and authentication paths allow the verifier to reconstruct its roots and then a FORS public key. A WOTS+ signature authenticates that public key. Its Merkle path reaches a subtree root, which another WOTS+ key authenticates at the next layer. Repeating this process connects the message to the public top root.

A signature therefore carries R, the FORS material and a sequence of WOTS+ signatures/Merkle paths. Verification rebuilds the public root; it does not decrypt a message. SHA2 and SHAKE variants, security levels and the “s”/“f” trade-off change sizes and speed. “s” prioritizes smaller signatures; “f” prioritizes faster operations.

Stateless means the signer does not maintain an incrementing leaf-use counter across calls. The complete construction makes unsafe reuse sufficiently unlikely within its security limits; it does not permit arbitrary reuse of a bare WOTS+ key. Implementations still need correct seeds, addresses/domain separation, parameter limits and protection against faults and leakage.

05 / ALGORITHM FIELD NOTES

FN-DSA / Falcon: compact signatures through a lattice trapdoor

Falcon is a hash-and-sign construction over NTRU lattices. Secret short polynomials f,g,F,G satisfy fG−gF=q, and h=g/f mod q is public. These secrets provide an efficient lattice trapdoor. The original Falcon parameters use q=12289 and n=512 or 1024; they should not be read as a finalized FN-DSA API or encoding.

c = HashToPoint(salt, M) Find short (s₁,s₂) with s₁ + s₂h ≡ c (mod q). Verifier reconstructs s₁ = c − s₂h and checks ||(s₁,s₂)||² ≤ bound.

Many long vectors satisfy the public equation; producing a suitably short one is the hard part. The trapdoor lets the signer sample a short preimage from the required discrete Gaussian distribution using fast Fourier sampling. The wire signature encodes the salt and compressed s₂, not both full polynomials. Verification is largely public polynomial arithmetic and a norm check.

Its compact signatures come with a demanding signing implementation: Gaussian sampling, FFT precision, encoding/rejection and timing behavior all matter. A mathematically correct sampler that leaks secret-dependent information is not a secure implementation. Contrast ML-DSA’s masked challenge/response with Falcon’s trapdoor preimage sampling; they are different lattice-signature designs.

Status checked 5 November 2026: NIST still lists FIPS 206 as in development. Learn Falcon’s structure from its submission specification, and follow NIST for FN-DSA naming, final parameters and conformance requirements.

06 / ALGORITHM FIELD NOTES

HQC: sparse binary masks meet error-correcting codes

HQC is a code-based KEM built around quasi-cyclic decoding problems. Work in the binary cyclic ring F₂[X]/(Xⁿ−1): addition/subtraction is XOR and multiplication is cyclic convolution. Secret low-Hamming-weight vectors x,y and a public random h define s=x+hy. The sender uses fresh sparse r₁,r₂,e to mask an encoded internal message.

T = the specified truncation to the codeword length s = x + hy u = r₁ + hr₂ v = C(m) + T(sr₂ + e) v − T(uy) = C(m) + T(xr₂ + e − r₁y)

Knowing y cancels the large shared term. The residual error can be decoded with the public concatenated code: outer Reed–Solomon encoding, then repeated Reed–Muller encoding; decoding reverses that order. The error-correcting code itself is not secret. Without the secret mask, recovering the appropriate sparse structure or distinguishing the masked relation is tied to the specified quasi-cyclic hard problems.

The full KEM uses a salted Fujisaki–Okamoto-style transform: derive the PKE coins from the encapsulated message and required context, recover a candidate message, re-encrypt, and select the valid or fallback shared secret. Raw HQC-PKE is not the whole chosen-ciphertext-secure KEM. Decoding-failure probability, constant-time decoding and input validation are critical implementation properties.

NIST selected HQC on 11 March 2025 to diversify KEM assumptions beyond lattices. This lesson follows the project specification dated 12 October 2026; its parameters and encodings may differ from older “HQC-128” examples. Selection, project-specification updates and publication of a NIST standard are separate milestones.

07 / ALGORITHM FIELD NOTES

LMS / XMSS: every one-time key needs a one-time allocation

A one-time signature (OTS) authenticates at most one distinct message per key. Winternitz-style schemes encode message-digest digits plus a checksum using positions on one-way hash chains. A signature reveals intermediate chain values; verification hashes forward to recover the public endpoints. Reusing that key for different messages can expose combinations useful for a forgery. The checksum and domain-separated chain functions are essential.

ConstructionOTS + tree mechanismWhat the signature contains
LMSLM-OTS public keys authenticated by an LMS Merkle treeLeaf q, LM-OTS signature, algorithm identifiers and authentication path
XMSSWOTS+; address-dependent hashing and L-tree compression of the OTS public keyLeaf index, randomizer, WOTS+ signature and authentication path
HSS / XMSSᴹᵀHierarchies of LMS / XMSS trees authenticate lower-level rootsA chain of authenticated subtrees; finite capacity remains

For a single height-h Merkle tree, 2ʰ OTS leaves provide at most 2ʰ distinct-message signing slots. The public root stays fixed, but the signer’s next-unused-leaf state changes. Verification derives an OTS public key from the signature and hashes the authentication path to the trusted root; the verifier does not need to track the signer’s next index.

Treat leaf allocation like a security-critical transaction. Concurrent requests, a restored backup, cloned VM or a rolled-back disk can reuse an OTS key. Use the profile’s required hardware/module controls, durable monotonic allocation and a tested exhaustion/rotation plan. A crash may safely burn an index; it must not make that index available again. Distributed signers need explicit non-overlapping allocation and recovery rules.

LMS/XMSS and their multi-tree variants are covered by SP 800-208 under its approved parameter and operational restrictions; RFC 8554 and RFC 8391 describe the constructions. Controlled firmware or release signing is a useful setting to study. They are not a drop-in replacement for every high-concurrency signing service, and are signature schemes rather than KEMs.
