01 / ALGORITHM FIELD NOTES

六类算法，多种安全假设

先弄清这些对象是什么

公钥是有结构的数据，不一定是一个整数或曲线点。私钥容器也可能缓存公开字段；签名是另一个计算输出，并不是“加密后的私钥”。下文的元组表示包含的内容，Pack/Encode 才生成规范规定的字节串。

对象 / 可见性包含什么各字段的作用
KEM：ML-KEM / HQCKeyGen → (ek, dk); Encaps(ek) → (K, c); Decaps(dk, c) → K′ek 公开，dk 私有；传输的是密文 c，不是共享秘密 K；没有签名输出。
数字签名KeyGen → (pk, sk); Sign(sk, M) → σ; Verify(pk, M, σ) → boolpk 公开，sk 私有；消息 M 与签名 σ 一同交给验证方。公钥属于谁，仍须由协议另行认证。

记号：|| 表示字节串拼接，帽号表示 NTT 表示；M 是应用消息，KEM 中的 m 则是新鲜内部随机值。同一字母在不同算法中可能含义不同。所有例子都假设事先确定参数组；H/G/J/PRF 是规范中不同的函数，不能任意替换。

PQC 是一组运行在经典计算机上、旨在抵抗已知经典与量子攻击的密码构造，并非单个算法，也不需要量子计算机。阅读每条路线时回答四个问题：解决什么用途、攻击者面对什么困难、合法方如何计算、实现必须保留哪些条件？

02 / ALGORITHM FIELD NOTES

ML-KEM：消去结构化掩码，再校验密文

ML-KEM · 对象与操作

接收方持有 ek 与 dk，任何获得已认证 ek 的发送方都可以向其封装新鲜秘密。dk 是完整解封密钥包，并非只有一个小秘密向量。

对象 / 可见性包含什么各字段的作用
公钥 · 可公开ek = Encode(t̂) || ρρ 用于展开公开矩阵 A；t̂ 是 t=As+e 的 NTT 编码，不必传输完整 A。
私钥 · 保密保存dk = dkPKE || ek || H(ek) || zdkPKE 编码 ŝ；缓存的 ek 与 H(ek) 用于重加密，秘密 z 用于生成隐式拒绝密钥。
密文 · 传输c = c1 || c2 = Pack(Compress(u), Compress(v))u 是多项式向量，v 是多项式；这是 KEM 密文，不是签名，也不是业务数据密文。
共享秘密 · 不传输K / K′: 32 bytes诚实生成的密文使两端得到相同 K；重加密校验失败时选择回退密钥。

机制为什么成立

ML-KEM 在 Rq = Zq[X]/(X²⁵⁶+1)、q=3329 上运算，多项式向量组成模。公开矩阵 A 由种子展开，小秘密和误差向量形成 t=As+e。由这些公开带噪关系恢复 s 与 Module-LWE 困难问题相关。不同参数组改变模秩及噪声、压缩参数。NTT 用于加速多项式乘法，本身不是安全假设。

Teaching view of the internal PKE: t = As + e u = Aᵀr + e₁ v = tᵀr + e₂ + Encode(m) v − sᵀu = Encode(m) + eᵀr + e₂ − sᵀe₁ (mod q)

较大的公共项相消，剩下编码消息和受控噪声；在规定误差界内，舍入可恢复 m。上式省略精确 NTT 表示、压缩及序列化，不能直接当实现。内部 K-PKE 也不是可独立暴露的获批加密服务。

封装选取新鲜的 32 字节内部随机消息 m，结合公钥哈希导出候选共享秘密与加密随机性，再加密 m。解封恢复 m′、重新导出这些量、重加密并比较 c′ 与 c。编码合法但比较失败的密文通过隐式拒绝选择规范规定的秘密派生回退密钥；密钥、密文长度与格式仍须检查，拒绝行为不能泄漏秘密相关信息。

ML-KEM-512/768/1024 都输出 32 字节共享秘密，名称后缀不是共享秘密长度。认证及绑定握手上下文的密钥派生由协议负责；KEM 自身不能防止未认证公钥被替换。

03 / ALGORITHM FIELD NOTES

ML-DSA：挑战、掩码响应与有条件的中止

ML-DSA · 对象与操作

公钥包含矩阵种子和舍入后的公开向量；签名包含挑战摘要、掩码响应和纠正 hint。验证方重建挑战，不会获得签名掩码 y 或秘密向量。

对象 / 可见性包含什么各字段的作用
公钥 · 可公开pk = Pack(ρ, t₁)ρ 展开 A；Power2Round 将 t=As₁+s₂ 分为 t=2^d·t₁+t₀，公钥只携带 t₁。
私钥 · 保密保存sk = Pack(ρ, K, tr, s₁, s₂, t₀)s₁、s₂ 是小秘密向量，t₀ 是低位部分；K 是秘密掩码派生种子，不是 KEM 共享秘密；tr=H(pk) 是缓存的公钥哈希。
签名 · 可公开σ = (c̃, z, hint)c̃ 是挑战哈希摘要，经 SampleInBall 映射为多项式 c；z=y+c·s₁；hint 是稀疏比特向量。不会传输 y 或完整多项式 c。
消息与上下文M, ctx; μ = H(tr || EncodePure(ctx, M))ctx 及 pure/prehash 模式必须一致；μ 是内部消息代表值，不是额外的签名字段。

机制为什么成立

ML-DSA 使用次数为 256、q=8380417 的多项式环，在 Fiat–Shamir 签名中结合 Module-LWE 相关隐藏性与短关系困难性。秘密包含小向量 s₁、s₂，公开关系为 t=As₁+s₂。签名掩码 y 产生承诺 w=Ay；消息代表值 μ 包含规定的公钥与消息上下文。

Unrounded teaching relation: c ← challenge(μ, HighBits(Ay)) z = y + c·s₁ Az − c·t = Ay − c·s₂ Actual public key: t₁ = rounded high bits of t; signature includes hints.

对 μ 和 HighBits(w) 哈希后，经 SampleInBall 得到稀疏多项式挑战 c，将承诺与消息绑定；响应 z 让验证方无需知道 y 或秘密即可重建所需高位。实际公钥传输舍入后的 t₁，因此还要用有界 hint 修正舍入丢失的高位信息。验证须检查挑战一致性、响应范数、hint 重量及编码，不能只检查一个代数等式。

签名会拒绝边界不合适的尝试并重新取掩码，以防输出分布泄漏秘密并保证验证正确。为加速而删去拒绝条件会改变方案。FIPS 204 支持对冲随机与确定性签名变体，但二者都必须正确派生掩码并执行域分离。

ML-DSA-44、65、87 依据矩阵维度命名，不是签名位数。Pure ML-DSA 与 HashML-DSA 是不同标准接口，不能随意替换为自定义预哈希。应分别审查算术、拒绝循环、随机数、故障及侧信道行为。

04 / ALGORITHM FIELD NOTES

SLH-DSA：哈希链、森林与被认证的超树

SLH-DSA · 对象与操作

公钥由公开哈希种子与顶层 Merkle 根组成；私钥额外包含两个秘密种子。签名是一组将消息连接到该根的哈希证明材料，不是仅有一个根值。

对象 / 可见性包含什么各字段的作用
公钥 · 可公开PK = (PK.seed, PK.root)PK.seed 用于带地址的公开哈希运算，PK.root 是可信顶层根；两者均为公开 n 字节串。
私钥 · 保密保存SK = (SK.seed, SK.prf, PK.seed, PK.root)SK.seed 派生 FORS/WOTS+ 秘密元素；SK.prf 用于生成消息随机化值 R；SK 缓存公开字段以便签名。
签名 · 可公开SIG = R || SIG_FORS || SIG_HTR 是公开随机化数据；SIG_FORS 包含选中秘密值与路径；SIG_HT 包含各层 WOTS+ 签名及认证路径。
内部索引(md, idx_tree, idx_leaf) = Split(H_msg(...))验证方由 R、PK 与 M 重算索引；它们不是签名调用间持续递增的状态计数器。

机制为什么成立

SLH-DSA 依赖哈希构造，而非格方程。公钥包含公开种子和顶层 Merkle 根，秘密种子派生底层大量签名秘密。每次签名先计算消息相关随机化值 R，再由摘要选择 FORS 叶和大型超树中的位置。

FORS 用多个小树组成的森林签署摘要比特：选中的秘密值和认证路径使验证方恢复各树根，再得到 FORS 公钥。WOTS+ 签名认证这个公钥，Merkle 路径通向子树根；上一层 WOTS+ 再认证该根。逐层重复，将消息连接到公开顶层根。

因此签名携带 R、FORS 材料，以及一串 WOTS+ 签名和 Merkle 路径。验证通过重建公开根完成，并非解密消息。SHA2/SHAKE 变体、安全级别及 s/f 取舍改变尺寸与速度：s 优先较小签名，f 优先较快操作。

无状态是指调用间无需维护递增的已用叶计数器。完整构造使安全限制内的不安全复用概率足够小，不表示裸 WOTS+ 密钥可以任意复用。实现仍须正确处理种子、地址与域分离、参数限制，并防护故障及泄漏。

05 / ALGORITHM FIELD NOTES

FN-DSA / Falcon：用格陷门得到紧凑签名

Falcon / FN-DSA · 对象与操作

这里采用 Falcon v1.2 提交设计解释 FN-DSA 的来源。公钥是多项式 h，秘密为一组短 NTRU 基；签名传输盐值和一条压缩短多项式，不传输这组基。

对象 / 可见性包含什么各字段的作用
公钥 · 可公开pk = h = g/f mod (Xⁿ+1, q)约定环上模 q 的公开多项式，编码形式另带算法/次数标识。
私钥 · 保密保存(f, g, F, G); optional FFT basis and LDL tree概念陷门包含四条多项式；序列化私钥可保存 f、g、F 并重建 G；展开的采样器数据同样属于秘密。
签名 · 可公开sig = (salt, EncodeCompressed(s₂))salt 决定公开哈希目标 c；只传输 s₂，验证方计算中心化 s₁=c−s₂h mod q；规定的头部及填充另由编码处理。
内部采样对(s₁, s₂): s₁+s₂h=c mod q两条多项式共同满足范数界；s₁ 不是额外传输的签名字段。

机制为什么成立

Falcon 是 NTRU 格上的 hash-and-sign 构造。秘密短多项式 f、g、F、G 满足 fG−gF=q，公开 h=g/f mod q，这些秘密提供有效的格陷门。原始 Falcon 使用 q=12289、n=512 或 1024；这些参数不能代替尚未定稿的 FN-DSA 接口和编码。

c = HashToPoint(salt, M) Find short (s₁,s₂) with s₁ + s₂h ≡ c (mod q). Verifier reconstructs s₁ = c − s₂h and checks ||(s₁,s₂)||² ≤ bound.

满足公开等式的长向量很多，难点是生成足够短的向量。签名方凭陷门，通过快速傅里叶采样从规定离散高斯分布中采样短原像。实际签名编码盐值和压缩后的 s₂，不是传输两条完整多项式。验证主要进行公开多项式算术及范数检查。

紧凑签名伴随更高的签名实现要求：高斯采样、FFT 精度、编码/拒绝及时间行为都重要。数学正确但泄漏秘密相关信息的采样器仍不安全。ML-DSA 的掩码挑战/响应与 Falcon 的陷门原像采样是不同格签名设计。

2026 年 11 月 5 日核对：NIST 仍将 FIPS 206 列为制定中。可用 Falcon 提交规范学习结构；FN-DSA 的名称、最终参数及符合性要求应跟踪 NIST。

机制为什么成立

HQC 是围绕准循环解码困难问题构造的编码型 KEM。在二进制循环环 F₂[X]/(Xⁿ−1) 中，加减为 XOR，乘法为循环卷积。秘密低汉明重量向量 x、y 与公开随机 h 定义 s=x+hy，发送方用新鲜稀疏 r₁、r₂、e 掩蔽编码后的内部消息。

T = the specified truncation to the codeword length s = x + hy u = r₁ + hr₂ v = C(m) + T(sr₂ + e) v − T(uy) = C(m) + T(xr₂ + e − r₁y)

知道 y 可消去大的公共项，剩余误差由公开级联码纠正：先外层 Reed–Solomon 编码，再重复 Reed–Muller 编码；解码顺序相反。纠错码本身不保密。不知道秘密掩码时，恢复相应稀疏结构或区分掩蔽关系，与规范所述准循环困难问题关联。

完整 KEM 采用加盐的 Fujisaki–Okamoto 类转换：由被封装消息及规定上下文派生 PKE 随机性，恢复候选消息后重加密，再选择有效或回退共享秘密。裸 HQC-PKE 不等于完整的抗选择密文攻击 KEM。解码失败概率、恒定时间解码及输入验证都是关键实现属性。

NIST 于 2025 年 3 月 11 日选中 HQC，用于增加格以外的 KEM 假设。本节采用项目 2026 年 10 月 12 日版规范，参数和编码可能与较早的 HQC-128 示例不同。被选中、项目规范更新和 NIST 标准发布是三个不同节点。

共有的 Merkle 树与状态管理原理

一次性签名（OTS）的每把密钥最多认证一个不同消息。Winternitz 类方案把消息摘要的数字及校验和编码为单向哈希链上的位置；签名揭示中间值，验证沿链向前哈希以恢复公开端点。为不同消息复用密钥可能泄漏可组合伪造的信息。校验和及域分离的链函数不可省略。

构造OTS 与树机制签名包含什么
LMS用 LMS Merkle 树认证 LM-OTS 公钥叶 q、LM-OTS 签名、算法标识及认证路径
XMSSWOTS+；依地址的哈希及用于压缩 OTS 公钥的 L-tree叶索引、随机化值、WOTS+ 签名及认证路径
HSS / XMSSᴹᵀLMS / XMSS 树层级认证下层根被认证子树链；容量仍有限

单棵高度 h 的 Merkle 树有 2ʰ 个 OTS 叶，最多提供 2ʰ 个不同消息签名槽位。公开根不变，签名端的下一未用叶状态却不断变化。验证方由签名恢复 OTS 公钥，再沿认证路径哈希至可信根，不需要记录签名端的下一个索引。

把叶分配当作安全关键事务。并发请求、恢复备份、克隆虚拟机或磁盘回滚都可能重用 OTS 密钥。应按具体配置要求使用硬件/模块控制、可持久化的单调分配，以及经过测试的耗尽/轮换方案。崩溃可以安全地浪费索引，但不能让它重新可用。分布式签名端还须规定互不重叠的分配和恢复规则。

SP 800-208 在规定参数及操作限制下覆盖 LMS/XMSS 及其多树变体；RFC 8554 和 RFC 8391 描述构造。可用受控固件或版本签名场景来学习，但不能把它们直接替换进所有高并发签名服务。它们是签名算法，不是 KEM。
